# Languages

The app is available in Finnish, English and Swedish. Finnish is the base language and the only
one crawlers, prerendered pages, share images and per-product feeds use. English and Swedish
exist only in the browser.

There are two separate parts:

| What                                  | Where it comes from                               | Where it lives                                          |
| ------------------------------------- | ------------------------------------------------- | ------------------------------------------------------- |
| Interface text (buttons, headings…)   | Written by us                                     | `messages/{fi,en,sv}.json`, compiled by Paraglide       |
| Product data (categories, countries…) | Alko's own translations, fetched after every sync | `labels.{en,sv}.json` next to `data.json` on `gh-pages` |

## Choosing the language

The language is stored in `localStorage['locale']` and read once when the page loads
(`src/lib/i18n/index.ts`). Changing it reloads the page, so `locale` never changes while the app
runs and code can read it as a constant.

- With nothing stored, the app is in Finnish. It never follows the browser language by itself:
  URLs carry no language, so a crawler (Googlebot renders pages with an English browser) would
  otherwise index the site in English while the prerendered stubs are Finnish.
- Visitors whose browser prefers English or Swedish get a one-time prompt in that language
  (`LanguageBanner.svelte`). Answering it, either way, or picking a language in the settings sets
  `language_banner_dismissed`. Paraglide itself writes `locale=fi` on the first visit, which is
  why the prompt can't use `locale` to tell whether someone chose.
- The picker is in Settings → More settings.

`<html lang>`, number and date formatting (`intlLocale`: `fi-FI`, `en-GB`, `sv-FI`), Chart.js
and the links to alko.fi (`src/lib/utils/app/alkoLinks.ts`) follow the language.

## Interface text

[Paraglide JS](https://inlang.com/m/gerre34r/library-inlang-paraglideJs) compiles
`messages/*.json` into one tree-shakeable function per message in `src/lib/paraglide/`
(generated, not committed). Options are in `project.inlang/paraglide.config.js`; the message
format plugin is loaded from `node_modules`, not a CDN, so builds don't fetch anything.

```svelte
<script lang="ts">
	import { m } from '$lib/i18n';
</script>

<p>{m.products_count({ count: 3 })}</p>
```

- Message keys are `area_what` in snake case (`nav_categories`, `daily_question_price`).
- `{name}` placeholders are inputs. Plurals use Paraglide's variant form; `products_count` is
  an example to copy. `{countNumber}` is the count formatted for the language.
- Sentences with a link or bold text in the middle are split into `_before`/`_link`/`_after`
  messages so each language can order them. A fragment can be empty.
- Messages called at module level (`columnDisplayNames`, the badge definitions…) are fine,
  because the language never changes during a page load.
- `tests/i18n/messages.test.ts` fails when a language is missing a message or uses different
  placeholders, since Paraglide would silently fall back to Finnish.

`bun install` compiles the messages (`prepare`), and `bun run i18n` does it on demand. Vite
recompiles on change in dev. The CI setup action compiles explicitly so a broken message fails
the job.

### Adding or changing text

1. Add the key to `messages/fi.json`, then the same key to `en.json` and `sv.json`.
2. Use it as `m.your_key()`.
3. `bun test tests/i18n` checks the three files agree.

## Product data

`data.json` stays Finnish. Its values are filter values, URL parameters (`/?Tyyppi=Viinit`),
category slugs and list contents, and the daily game hashes them, so they can't change with the
language. Values are translated only where they're shown, with `translateValue(value, column)`
and `productName(product)` from `src/lib/i18n/values.ts`. `formatValue` translates string
and set values of a known column itself.

### The label files

`scripts/i18n/labels.ts` (`bun run labels`) writes `labels.en.json` and `labels.sv.json`:

```jsonc
{
	"generated": "2026-10-15T03:58:00.000Z",
	// Lowercased Finnish value → Alko's translation
	"labels": { "punaviinit": "red wine", "paahteinen": "toasted, roasted" },
	// Product number → name, only where Alko's name differs from the Finnish one
	"names": { "700433": "Krombacher Pils can" }
}
```

How it fills them:

- **Search API, swept once per language** (`?lang=en`): categories, countries, taste styles,
  packaging, closures, selections, certificates and product names. Labels are paired per
  product, through their ids, since some ids have several labels (`selectionType_001` is both
  vakiovalikoima and kausituote). The most common pairing wins.
- **Taste words** (`Luonnehdinta`) have no ids. They're paired by position when the Finnish and
  translated lists are the same length, then by elimination: when everything else in a product's
  list is known, the leftover words pair up, joined when Alko's translation itself has a comma
  ("paahteinen" → "toasted, roasted").
- **Detail API** (`?lang=en`), for values the search API doesn't have: beer and cider styles,
  notes (`Huomautus`) and regions. Only values without a translation yet are fetched, one sample
  product each, at most `--detail-limit` (150) products per run.
- **Food pairings** are only on Alko's product pages, so their names are kept by hand in
  `FOOD_PAIRING_TRANSLATIONS` (`src/lib/utils/catalog/food.ts`).
- **Manual labels** in `MANUAL_LABELS` fill the few values Alko has no translation for at all.

Each run merges into the previous file, so values of removed products keep their translations
and the detail fetches only cover what's new. Values that read the same in both languages are
kept too, so they count as checked. The pure pairing logic is in `scripts/i18n/pairing.ts` and
tested in `tests/i18n/labels.test.ts`.

In CI, `fetchData.yml` seeds the previous files from `gh-pages`, runs the script after the
sync as a best-effort step, and deploys the files with the dataset. If Alko's English or
Swedish data can't be fetched, the previous files stay. In the app, a missing file just means
the data is shown in Finnish.

The files are about 45 KB gzipped each, loaded in parallel with `data.json` only for English
and Swedish.

### Coverage and fallbacks

- Coverage of products in the selection is close to complete. Anything without a translation
  is shown in Finnish.
- Product names: Alko's translation, or for removed products the Finnish name with its trailing
  packaging word translated ("tölkki" → "can"), which is how most translated names differ.
- Producers, grapes and appellations are proper nouns and aren't translated.
- Stores: Swedish uses Alko's `name_sv`, `address_sv` and the other `_sv` fields
  (`storeText` in `src/lib/utils/catalog/availability.ts`). The Finnish name stays the store
  filter's value; `registerStoreNames` maps it for display.
- Search matches both the Finnish and the shown product name.

## What stays Finnish

- Prerendered stubs, OG images, `sitemap.xml`, meta descriptions and keywords: these are what
  crawlers see.
- URLs and URL parameters.
- Per-product and per-category RSS feeds. The aggregate feeds also exist as `rss.en.xml`,
  `feed.en.json`, `rss.sv.xml` and `feed.sv.json` ([Site generation](site-generation.md#feeds)),
  and Settings → About links the visitor's language.
- Site notices, unless the notice has `translations` (see `schemas/notices.schema.json`).
- `data.json` and everything stored in the browser.

## Bundle size

Each compiled message holds all three languages. On release this added about 16 KB gzipped to
the JS the first page load preloads (84 → 100 KB) and 44 KB to the whole app. Paraglide can
only drop the unused languages with a separate build per language, which a single static site
can't serve.
